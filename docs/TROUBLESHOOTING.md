# Troubleshooting

Start here:

```bash
agent-handoff doctor
agent-handoff doctor --json
agent-handoff list
```

Useful files under `$AGENT_HANDOFF_HOME`:

```text
logs/integration.log
logs/upload.log
queue/*.json
state/sessions.json
state/index_upload.json
state/dispatch/notifications/records/*.json
config/config.json
```

Never paste tokens or rclone configuration contents into chat or logs.

## Installation refuses invalid OpenCode or AGY JSON

The installer validates managed external JSON before changing any plugin, hook, or instruction file. If it reports `invalid opencode.json` or `invalid AGY hooks.json`, fix the JSON first:

```bash
python3 -m json.tool ~/.config/opencode/opencode.json
python3 -m json.tool ~/.gemini/config/hooks.json
```

A failed installation restores the managed integration files it had already changed. Existing `*.backup-agent-handoff-*` files remain available for inspection.

## Rollback refuses a legacy snapshot

A snapshot created before ownership manifests has no `manifest.json`. The rollback refuses it because newer managed files cannot be separated safely from unmanaged files. Install or upgrade once with the current version to create a snapshot with ownership information, then roll back to that snapshot. Runtime configuration and data are never modified by the refusal.

## Installer reports an unsafe managed path

The installer never follows source symlinks or writes through destination symlink components. If it reports an unsafe managed path, inspect the runtime paths involved and replace the symlink with a normal directory before retrying. Do not delete runtime data or configuration directories.

## Guided setup reports missing or blocked checks

Run `agent-handoff setup plan --json` first. Checks are scoped to `core`, `install`, `capture`, `dispatch`, or `coding`; `missing` is an actionable setup step, while `blocked` means the host or configuration is not usable until it is fixed. `ok` covers core and install blockers only. Optional dispatch or coding prerequisites do not stop core capture.

Choose one path for missing prerequisites:

- missing rclone: install it and re-run the plan;
- no Drive authorization: run `agent-handoff auth` or import a mode-600 token file produced by `rclone authorize "drive"`;
- no project: run `agent-handoff project add` after Drive authorization;
- missing GitHub authorization for dispatch: run `gh auth login` with your own account;
- missing OpenCode: install it only if you want automatic capture or dispatch.

## Guided setup reports an invalid configuration

`setup plan` and `setup apply` fail closed when the runtime configuration is invalid JSON or fails the existing core, dispatcher, or notification validators. Guided setup never overwrites an invalid file blindly. Restore a valid file from your own backup or fix the reported error, then re-run the plan.

A symbolic-link configuration is also refused; replace it with a regular mode-600 file before applying changes.

## Guided setup requires approval

`setup apply` changes configuration only with `--approve`. Without it, the command prints a plan or JSON preview, sets `approval_required: true`, and exits non-zero. Review the proposed `config_plan.changes`, then rerun with `--approve`.

Applying setup values never enables the dispatcher, coding, `workspace_write`, isolation, notifications, or a systemd service.

## Guided setup was interrupted

If `setup plan --json` reports `setup.recovery.required: true`:

1. read `recovery.status` and `recovery.reason`;
2. do not delete the journal or edit the configuration by hand;
3. run `agent-handoff setup recover --approve --json`;
4. re-run `agent-handoff setup plan --json` and `agent-handoff config validate --json`.

`setup recover` finalizes cleanup only when the current file hash matches the recorded previous or proposed state. An `ambiguous` state is preserved for manual review and is never guessed.

A retained `.backup-setup-*` file is the recoverable pre-apply configuration.

## Google Drive is not authorized

Symptoms:

- `doctor` reports `Google Drive access: rclone config not found` or `Not ready`.
- Queue items show `Google Drive unavailable`.
- `agent-handoff auth --check` exits nonzero.

Fix:

```bash
agent-handoff auth
setup/gdrive-auth.sh
```

Use the token import flow described by the command. The import verifies Drive before keeping the config. Then:

```bash
agent-handoff auth --check
agent-handoff doctor
agent-handoff retry-upload --force
```

## The remote exists but uploads fail with auth errors

Possible causes:

- Expired or revoked refresh token.
- Token generated by a different OAuth client or incompatible rclone version.
- The Google account cannot access the folders.
- A folder was moved or deleted.

Fix:

1. Re-run `rclone authorize "drive"` on a browser-capable machine.
2. Import the new token with `agent-handoff auth --import-token-file`.
3. Run `agent-handoff auth --check`.
4. Run `agent-handoff retry-upload --force`.

The import restores the previous rclone config if the new token cannot access Drive.

## Token import fails and the config is restored

That is intentional. Check:

- The token file is valid JSON.
- It contains `access_token` and/or `refresh_token`.
- The Google account can open the configured Drive root.
- The rclone versions on the browser machine and this host are compatible.
- The file contains only the JSON object, without surrounding prose.

## Drive folder ID check fails

`doctor` or `retry-upload` refuses to upload when a configured folder ID is not a direct child of the reports root.

```bash
agent-handoff project list --check
agent-handoff project add --name "Project" \
  --folder-id "<verified-folder-id>" --path /path/to/project
```

If duplicate folders with the same name exist, the system refuses to guess. Supply the exact folder ID.

## Queue is stuck

Inspect queue metadata without printing report contents:

```bash
python3 - <<'PY'
import glob, json, os
from pathlib import Path
root = os.environ.get("AGENT_HANDOFF_HOME", str(Path.home() / "agent-handoff"))
for path in sorted(glob.glob(root + "/queue/*.json")):
    data = json.load(open(path))
    print(data.get("id"), data.get("kind"), data.get("project"), data.get("run_id"),
          "attempts:", data.get("attempts"), "error:", data.get("last_error"),
          "next:", data.get("next_attempt_at"))
PY
```

Then:

```bash
agent-handoff retry-upload --force
agent-handoff retry-upload --force --project Project
```

Backoff is automatic. `--force` ignores the timer. Do not delete report directories; the queue can retry indefinitely.

## Upload verified but the file is not where expected

Check the remote path recorded in `COMPLETE.json`:

```bash
python3 - <<'PY'
import glob, json, os
from pathlib import Path
root = os.environ.get("AGENT_HANDOFF_HOME", str(Path.home() / "agent-handoff"))
for path in glob.glob(root + "/data/projects/*/TASKS/*/RUNS/*/COMPLETE.json"):
    data = json.load(open(path))
    print(data["task_id"], data["run_id"], data["upload"]["verified"], data["report"]["remote_path"])
PY
```

Verify with rclone manually (read-only):

```bash
rclone lsf "gdrive,root_folder_id=<PROJECT_FOLDER_ID>:TASKS/<TASK_FOLDER>/RUNS/<RUN_ID>/"
```

Do not use `rclone sync`.

## MD5 mismatch

Possible causes:

- Truncated or interrupted upload.
- rclone did not support MD5 for the object; read-back should be used automatically.
- A Drive conversion changed the object (not expected for `.md`/`.json`).

The run remains pending. Retry:

```bash
agent-handoff retry-upload --force --run <run-id>
```

## Index is missing or stale

```bash
agent-handoff index --project Project
agent-handoff index --project Project --upload
agent-handoff retry-upload --force
```

The uploaded index intentionally lists only upload-verified runs.

## OpenCode plugin did not create a report

```bash
agent-handoff doctor
ls -l ~/.config/opencode/plugin/agent-handoff.js
tail -50 "$AGENT_HANDOFF_HOME/logs/integration.log"
```

Reinstall:

```bash
python3 setup/install.py --home "$AGENT_HANDOFF_HOME"
```

Test with a small real session:

```bash
opencode run --dir /path/to/project -m <model> --title "Handoff plugin test" "Reply with exactly: PLUGIN_TEST_OK"
agent-handoff list --project Project
```

Notes:

- OpenCode must not be started with `--pure` if external plugins are expected.
- Subagent child sessions are skipped.
- A session with no assistant text is recorded as `blocked`, not `succeeded`.

## AGY hook did not create a report

Check the hook config:

```bash
python3 -m json.tool ~/.gemini/config/hooks.json
```

It should contain an `agent-handoff-report` entry whose command includes:

```text
agent-handoff hook agy
```

Test the hook manually:

```bash
printf '%s\n' '{"hookEventName":"Stop","conversationId":"manual-test","cwd":"/path/to/project","terminationReason":"NO_TOOL_CALL","fullyIdle":true,"lastUserInput":"manual hook test","error":""}' | agent-handoff hook agy
```

It must print `{}` and exit 0. If a report is created for a real conversation, the hook is working.

Notes:

- AGY writes hooks to `~/.gemini/config/hooks.json`.
- A `Stop` with `fullyIdle: false` is recorded as `blocked`.
- A conversation outside a mapped project does not create an automatic report.

## Duplicate reports

Possible causes:

- The same session idle event fired twice with a different fingerprint.
- A manual `complete` was run in addition to automatic capture.
- The session mapping file was deleted.

Check `AUTO.json` inside the task directory and `state/sessions.json`. Automatic capture deduplicates by event key. Do not delete duplicate evidence blindly; mark it superseded or leave it for audit.

## Disk is nearly full

Reports are small, but queue retries and logs can grow. Archive old local task data only after verifying it is uploaded and backed up. Do not delete the only copy of a pending report.

## Permissions

Expected:

```bash
chmod 700 "$AGENT_HANDOFF_HOME"
chmod 600 "$AGENT_HANDOFF_HOME/config/config.json"
chmod 600 "$AGENT_HANDOFF_HOME"/logs/*.log
chmod 600 ~/.config/rclone/rclone.conf
```

## Re-run tests

```bash
PYTHONPATH=lib python3 -m unittest discover -s tests -p "test_*.py" -v
python3 tests/acceptance.py
```

The acceptance suite uses an isolated `/tmp/agent-handoff-acceptance` home and a fake rclone remote for synthetic checks. Its live checks read the configured Drive hierarchy and do not create or delete Drive folders.

## Dispatcher is disabled

`agent-handoff dispatch run` refuses to start when `dispatch.enabled` is false. Core capture still works. Add the `dispatch` section to the runtime config; do not replace the whole config with an example.

```bash
agent-handoff config validate
```

## Dispatcher refuses the configuration

Common causes:

- `dispatch.repository` is not `owner/name`.
- The repository is public; v1.1 requires a private repository with Issues enabled.
- The authenticated `gh` user is not in `dispatch.allowed_users`.
- A dispatch project is not present in the core `projects` mapping.
- A dispatch workspace does not exactly match one of that project's recorded paths.
- A model alias is missing from `dispatch.models`.
- `workspace_write` was selected without `allow_write: true`, or `allow_write` was enabled with `read_only`;
- a project-level `workspace_write` omitted its own explicit `allow_write: true`;
- an unknown execution/isolation field or a non-boolean `allow_write` was used.

Fix the config and rerun:

```bash
agent-handoff config validate --json
agent-handoff doctor
```

## Issue request was rejected

The dispatcher rejects, without executing:

- missing or unsupported `handoff-version`;
- unknown or duplicate metadata fields;
- unknown project, agent, or model alias;
- `session: same` (SAME SESSION is deferred, never simulated);
- empty or oversized instructions;
- unauthorized authors.

A rejection comment is marker-idempotent. Editing a rejected issue does not automatically execute it; submit a new corrected issue.

## Dispatch record is NEEDS_ATTENTION

This means a process restarted after a claim/start and no recoverable session output was found. The agent is **not** rerun automatically.

Inspect without changing anything:

```bash
agent-handoff dispatch status --json
agent-handoff dispatch inspect --task <task-id> --run <run-id> --json
```

If the work must be repeated, submit a new issue. Do not edit the ledger to force a rerun.

## A dispatcher run was interrupted

An interrupt during a slow upload is safe. The durable record keeps the existing OpenCode session, task, and run identity; it normally remains `UPLOAD_PENDING` with capture complete. Do not submit a duplicate issue and do not delete the task directory. A later poll retries only the upload and publication:

```bash
agent-handoff dispatch status
agent-handoff dispatch run --once --progress
```

If the status says `stalled` because the dispatcher process is gone, the same command reconciles persisted session output without re-executing OpenCode. Use `--json` for scripts; progress is written to stderr.

## Upload is pending but the report is readable on Drive

A readable file is not upload verification. Check:

```bash
agent-handoff dispatch status --json
agent-handoff dispatch inspect --task <task-id> --run <run-id> --json
```

`dispatch status` reports `health=retryable`, `phase=retry_upload`, the next retry time, and whether only the upload will run. If local verification is missing, retry the upload only:

```bash
agent-handoff retry-upload --force --task <task-id> --run <run-id>
```

If local verification succeeded but the remote `COMPLETE.json` still says pending, reconcile and publish without rerunning the agent:

```bash
agent-handoff dispatch deliver --task <task-id> --run <run-id> \
  --issue <number> --repository owner/private-dispatch
```

This creates and verifies `UPLOAD-RECEIPT.json`, re-uploads truthful verified `COMPLETE.json`, and publishes the direct URL idempotently.

## GitHub publication failed

The report is safe; only the comment failed. The record remains `UPLOAD_VERIFIED` and retries automatically with backoff. `dispatch status` reports `health=retryable`, `phase=retry_publication`, the verified report link, and the next retry. Force a retry with:

```bash
agent-handoff dispatch run --once --force --json
```

Only the comment is retried; the verified upload is reused.

If `dispatch status` reports `health=attention` with `phase=publication_exhausted`, `dispatch.delivery.max_attempts` was reached. The verified upload is still intact. Publish manually without re-running the agent:

```bash
agent-handoff dispatch deliver --task <task-id> --run <run-id> --issue <number> --repository owner/private-dispatch --json
```

Before posting, the dispatcher checks for the delivery marker. A retry after an uncertain comment post does not create a duplicate link.

## Dispatcher status is ISSUE_UPDATED but I cannot see the comment

Confirm the record's `comment_url` and open the issue in the authenticated browser session. Private repository visibility is required. A comment URL is publication evidence, not upload verification.

## Telegram notifications are disabled

That is the default and does not affect capture or dispatch. To enable them, add the `notifications` section to the runtime config, keep the token in an environment variable named by `token_env`, then validate:

```bash
agent-handoff config validate
agent-handoff doctor
```

Do not put the bot token in `config.json`, an Issue, a report, a chat, or a log. Do not paste it into a terminal transcript.

A disabled configuration never creates a Telegram transport and never makes a network request.

## Telegram configuration is rejected

Common causes:

- `notifications.telegram.enabled` is true but `chat_id` is empty;
- the environment variable named by `token_env` is unset or empty;
- the value does not look like a bot token;
- the chat id is neither numeric (negative for groups/channels) nor `@channelusername`;
- a retry/timeout/attempt value is outside its bounded range.

Fix the config or environment and rerun:

```bash
agent-handoff config validate --json
```

Validation errors name the environment variable, never its value. The token is never printed.

## Task is delivered but the Telegram notification is pending

The report is safe. `dispatch status` keeps the task at `health=delivered` and shows the separate notification state. `RETRY_WAIT` retries automatically with backoff. Inspect without sending:

```bash
agent-handoff dispatch notify --json
agent-handoff dispatch notify --all --json
```

After fixing the cause, retry confirmed notification failures only:

```bash
agent-handoff dispatch notify --retry --json
agent-handoff dispatch notify --retry --task <task-id> --run <run-id> --json
```

A generic retry deliberately excludes ambiguous interrupted sends. This never reruns OpenCode, re-uploads a verified report, or reposts the GitHub comment.

## Telegram notification needs attention

`NEEDS_ATTENTION` means notification attempts were exhausted, the related dispatch record is unavailable, or an interrupted send has an ambiguous outcome. The task/report delivery is still valid. Read the safe error:

```bash
agent-handoff dispatch notify --json
agent-handoff dispatch status --json
```

For a confirmed token/chat/network/rate-limit failure, fix the cause and run `dispatch notify --retry`. For an ambiguous outcome, review the Telegram chat first; a targeted retry requires both the notification id and explicit acknowledgement of the duplicate risk:

```bash
agent-handoff dispatch notify --retry --notification <notification-id> --acknowledge-duplicate --json
```

The outbox does not pretend to offer mathematically guaranteed exactly-once delivery.

## Telegram send was interrupted

A send is persisted as `SENDING` before the HTTP request. If the process stops during the request, a later poll does not silently resend it. After the stale timeout it becomes `NEEDS_ATTENTION` with `ambiguous=true` and a warning that Telegram may or may not have accepted the message. Review the Telegram chat, then either ignore it or explicitly retry that one notification with `--notification <id> --acknowledge-duplicate`. A generic `dispatch notify --retry` will not resend it.

## Old reports were not sent when notifications were enabled

This is intentional. Notification enqueue happens at lifecycle transitions observed after enablement. Historical `ISSUE_UPDATED` records are never scanned or backfilled, even if a later metadata update changes their generic `updated_at`; reconciliation uses the real publication/attention/failure transition timestamp. This prevents a flood of old reports. Records that genuinely publish or enter attention after enablement may legitimately notify.

An unsent notification whose task condition later recovers is marked `SUPERSEDED` with a reason and timestamp, not sent and not deleted. If a historical record has no trustworthy transition timestamp, recovery fails closed rather than guessing.

## Telegram recipient cannot open the report link

The bot does not change Google Drive sharing. Private Drive files are visible only to accounts that already have access. The Telegram message contains a link; it is not a copy of the report and does not grant permissions.

## Tests and live checks

```bash
PYTHONPATH=lib python3 -m unittest discover -s tests -p "test_*.py" -v
```

Deterministic tests do not need Drive, provider, or Telegram credentials. They use fake GitHub, OpenCode, rclone, and a local fake Bot API. Live dispatch testing requires real `gh`, OpenCode provider auth, Drive auth, and (only for notification acceptance) an owner-provided bot token/chat id; if any are unavailable, report the limitation instead of claiming a pass.

## Isolated coding preflight failed

When `dispatch.execution.isolation.enabled` is true, the dispatcher refuses to start OpenCode unless the dedicated identity, child authentication, and workspace can be proven safe. Typical reasons:

- the configured Unix user or primary group does not exist;
- the user is root or belongs to a privileged group;
- the dispatcher itself is not running as root, so the UID/GID drop cannot be applied;
- the child HOME/XDG directories or `$XDG_DATA_HOME/opencode/auth.json` are missing, not child-owned, or group/world readable;
- the workspace is outside the configured roots, under `/root` or `$AGENT_HANDOFF_HOME`, symlinked, not owned by the dedicated identity, or not a Git workspace;
- the Git tree has uncommitted or untracked changes.

The record becomes `NEEDS_ATTENTION` without an OpenCode run. Nothing is reset, and the dispatcher never falls back to root or the parent identity. Fix the staging layout or authentication, then submit a new request. Do not edit the ledger to force a rerun. See `docs/SECURE-CODING.md`.

## Coding task is rejected as disabled

C2 coding requires both `dispatch.coding.enabled: true` and `coding.enabled: true` on the selected project, plus effective C1 isolation. If any is missing, the Issue is rejected with no agent run. Do not enable production coding to "test" it. Use an owner-approved staging project and follow `docs/SECURE-CODING.md`.

## Coding workspace preparation failed

The disposable workspace must be new, under the configured `coding.workspace_root`, owned by the dedicated identity, outside the source checkout, and cloned from a source whose `origin` matches the configured repository. Existing task directories, symlinks, dirty clones, a wrong base commit, or a mismatched remote fail closed. The active developer checkout is not reset or cleaned. Inspect the preserved task directory and durable stage; correct the trusted configuration or remove only the managed staging directory after review.

## Trusted coding tests failed

A failing or timed-out trusted test blocks commit, push, and Draft PR creation. The dispatcher preserves the workspace and test evidence, records `coding.blocked_stage=TESTING`, and still delivers an honest report with no PR. Fix the code/tests and submit a new Issue. The dispatcher does not promise a publishable PR for failing changes and does not rerun the agent indefinitely.

## Diff validation blocked the coding task

Changed paths may be protected, outside an allowlist, binary, symlinked, submodule-related, too large, or may contain obvious secret material. Secret values are redacted from evidence, but secret scanning is not proof of safety. Review the report and the preserved workspace. Adjust the trusted policy only if the change is genuinely intended; do not blindly add credential files or CI workflows to an allowlist.

## Draft PR creation or branch push failed

Publication retries are bounded. `dispatch status --json` shows `coding.stage`, `publication.attempts`, `next_attempt_at`, and `last_error`. A transient failure retries only the publish/PR step; it never reruns OpenCode or trusted tests. An existing branch with a different commit, a non-Draft PR, or multiple matching PRs fails closed and is never force-pushed or silently replaced. After retries are exhausted, use the preserved evidence and create a new task if a different code result is required.

## Coding task restarted during execution

If persisted OpenCode events exist, the dispatcher resumes from them and does not rerun the model. If no recoverable output exists, the record becomes `NEEDS_ATTENTION`; the workspace and session evidence are preserved. Do not delete the ledger or force a duplicate run. Inspect the host and submit a new Issue only if the work must be repeated.

## Upload failed after a Draft PR was created

The PR is already a durable review artifact. Upload/publication retries reuse the PR and the verified upload contract; the agent is not re-executed. If the report cannot be verified, the PR remains a Draft and the task is not claimed as delivered. Do not merge or deploy based on an unverified report.

## Coding artifact changed after validation

C2 records a SHA-256 digest, size, raw mode, and publication mode for every approved file. Publication re-reads the file with no-follow semantics and verifies the staged index and committed tree. If a file changes after validation, the task is blocked with no branch or PR. This is intentional: do not edit the task workspace while publication is running, and do not weaken digest checks. The agent is not rerun automatically.

## Coding publication staging is missing

If staging was lost after a commit but before the ledger recorded a push, the dispatcher queries the trusted remote branch by its stable task branch. If the remote already contains the exact verified commit, publication continues and records remote-SHA recovery. If the remote branch is absent or contains a different commit, the task becomes blocked for operator review; the dispatcher does not force-push and does not publish a different commit under the old task identity.

## Draft PR exists but the report link is missing from its body

Report and Issue delivery are independent of the PR body update. After verified report upload, the dispatcher attempts to add the verified report link to the existing Draft PR with bounded backoff. A failure is surfaced as a warning/status retry, never as a duplicate PR. If the bounded retry is exhausted, inspect the existing PR and the verified report; do not create a replacement PR.

## Coding process group outlived its command

Trusted tests and OpenCode run in their own process groups. A surviving group after command completion is terminated and blocks publication. This prevents workspace mutation after validation. A fully detached process that escapes the process group is not detected; use host-level monitoring for that residual risk.
